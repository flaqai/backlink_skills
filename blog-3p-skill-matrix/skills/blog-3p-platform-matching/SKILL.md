# 博客 3P：平台匹配调研

先阅读[术语约定](../../docs/terminology.zh-CN.md)。这是内容项目写前阶段唯一允许的可见子角色例外。当前 schema 2.14 的每篇文章都必须在 WQ/WR 派发前取得用户确认的人工发布平台/账号映射；本技能只研究用户已提供的 XLSX、表格或消息中出现的平台/账号候选，输出建议和不确定性；不创建文章交付目录、不写文章，不启动 WQ/WR，不注册/登录，不处理验证码，也不操作编辑器。

## 输入与边界

- 读取用户原始候选资料及其哈希、精确行/单元格/消息定位，冻结的文章语言、市场、内容类型和人工发布要求。
- 公开平台页面、政策、格式说明、语言支持、公开样本和历史证据只能说明可承接性；它们不能自行创建候选、账号映射或允许范围。
- 每个建议都必须保持“该文章 + 该平台 + 该账号”的一对一关系；不复用平台名或平台/账号组合，也不把已验证账号当成通用平台池。
- 对每篇候选明确分开两层证据：`primary_reader_languages` / `primary_reader_markets` 与其公开受众证据，和 `transport_supported_content_languages` 与其编辑器或格式传递证据。能显示、保存或阅读英语只属于后者，不能证明英语或全球英语是该平台的主读者受众。
- 已观察到的发布问题只能作为同一平台、同一账号、同类交接的传输风险问题，必须记录观察日期与读者页/编辑器面；它们不能替代读者语言、市场、需求、审核原因或账号授权证据。无同账号观察时，保持 `UNVERIFIED`，不要把其他账号或旧文章的结果外推为平台能力。
- 若文章语言或市场不匹配候选平台的主读者，提案只能标成需逐篇确认的 `CROSS_LANGUAGE_EXCEPTION_OWNER_CONFIRMED`，不能把它写成普通 `COMPATIBLE`。匹配子角色不能自行批准例外。
- 无法证明时写 `UNVERIFIED` 和风险，不臆造“热门”“支持”或登录/发布能力。任何付费、账号、政策、语言或格式疑点都清楚标出给用户决定。

## 输出

写入 `evidence/platform-matching/platform-matching-report.md` 和 `platform-matching-proposal.json`。对每篇文章说明：用户来源定位、候选平台/账号、文章语言/市场、主读者语言/市场及其证据、可观察到的传递语言支持及其证据、`fit_mode`、格式/人工传递适配、证据 URL/日期、限制、不确定性和建议。提案必须可追溯，却不能声明已冻结或已获授权。平台样本/画像最多帮助决定技术深度、语气、示例类型和交付形式；不能作为主关键词、自然变体、搜索意图、当地需求、热门度或选题成立的证据。

G 只检查来源和一对一结构，再向用户展示。只有用户把每一个 `{platform, account}` 明确确认到 `owner-platform-selection.json`，让 `platform_scope.allowed_pairs` 成为其机械投影，并为每篇填入兼容的语言－平台记录后，文章协作组才可启动。缺候选、无可靠建议或用户未确认时，结果为 `OWNER_DECISION_REQUIRED`；不得替用户选、换、补或扩展平台范围。历史 schema 2.8 可供读取或校验，但不能绕过当前人工发布映射要求。

按需读取[平台选择契约](../../docs/owner-platform-selection.md)的来源与确认条款；只有匹配平台存在实质读者传递风险时，才读取[平台样本画像](../../docs/platform-style-profiles.md)的相关段落。机器字段、JSON 键、状态码和路径保持不变。
